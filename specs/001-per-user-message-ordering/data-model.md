# Phase 1 Data Model: Per-User Message Ordering and Exclusivity

**Feature**: `001-per-user-message-ordering` | **Date**: 2026-08-24
**Spec**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Research**: [research.md](./research.md)

Everything the system needs to coordinate lives in one table. There is no separate claims table,
lock table, or queue table: the claim is a property of the message row, which is what lets a single
statement both select the next message and take exclusivity (R-001, R-002).

## Entities

### Message

The only persisted entity. Maps the spec's **Message** and **Processing claim** onto one row — the
claim is `state = 'Processing'` plus `claimed_at`, and it is released by the same update that
records a final state.

| Column | Type | Notes |
|--------|------|-------|
| `id` | `uuid` | Primary key. Generated by the application at acceptance and returned to the client (FR-009). No unguessability requirement (FR-020a), so a plain v4 UUID is used because it is convenient, not for secrecy. |
| `sequence` | `bigint` | `GENERATED BY DEFAULT AS IDENTITY`. Assigned at insert; the single source of acceptance order (FR-002, R-003). Gaps are expected and harmless. |
| `user_id` | `text` | Client-supplied, trusted (FR-020). The unit of ordering and exclusivity. |
| `content` | `text` | The submitted message. Never logged at any level (FR-021, R-009). |
| `state` | `text` | One of the four values below. Constrained by a `CHECK`. |
| `answer` | `text` NULL | Set only on transition to `Completed`. |
| `failure_reason` | `text` NULL | Set only on transition to `Failed`. Distinguishes a provider-reported failure from an expiry, which Principle II's inspectability requirement needs. |
| `accepted_at` | `timestamptz` | For reporting only — never used to order (R-003). |
| `claimed_at` | `timestamptz` NULL | When the current claim was taken. The expiry predicate reads this. Cleared on reaching a final state. |
| `finished_at` | `timestamptz` NULL | When a final state was recorded. |
| `claimed_by` | `text` NULL | Instance identity that claimed it. Diagnostics only — no correctness depends on it, and in particular nothing routes a callback by it (FR-006). |

`sequence`, `accepted_at`, `claimed_at`, and `finished_at` are all exposed on the status response
so that FIFO can be asserted from data rather than inferred from test timing (SC-002).

### State values

| State | Meaning | Terminal |
|-------|---------|----------|
| `Pending` | Accepted and waiting its turn. Unbounded time here is normal (spec Assumptions). | No |
| `Processing` | Claimed; submitted or about to be submitted to the language model. At most one per user. | No |
| `Completed` | An answer was recorded. | Yes |
| `Failed` | A failure was recorded — either provider-reported or claim expiry. | Yes |

### Permitted transitions

```text
                    claim (atomic)              callback: completed
   [ Pending ] ──────────────────────> [ Processing ] ──────────────> [ Completed ]
                                             │
                                             ├── callback: failed ──> [ Failed ]
                                             │
                                             └── claim expiry ──────> [ Failed ]
```

Rules that fall out of the spec and are enforced, not merely intended:

- No transition leaves a terminal state. `Completed` and `Failed` are final, which is what makes a
  duplicate callback a no-op (FR-014), a post-expiry callback harmless (FR-013b), and state
  regression impossible.
- No transition re-enters `Pending`. An expired message is never re-submitted (FR-013a), so there
  is no path back into the queue and each accepted message is submitted at most once.
- A row is never deleted (FR-023).

## Schema

```sql
CREATE TABLE IF NOT EXISTS messages (
    id             uuid        PRIMARY KEY,
    sequence       bigint      GENERATED BY DEFAULT AS IDENTITY,
    user_id        text        NOT NULL,
    content        text        NOT NULL,
    state          text        NOT NULL,
    answer         text        NULL,
    failure_reason text        NULL,
    accepted_at    timestamptz NOT NULL,
    claimed_at     timestamptz NULL,
    finished_at    timestamptz NULL,
    claimed_by     text        NULL,

    CONSTRAINT ck_messages_state
        CHECK (state IN ('Pending', 'Processing', 'Completed', 'Failed')),
    CONSTRAINT ck_messages_user_id_not_blank
        CHECK (length(btrim(user_id)) > 0),
    CONSTRAINT ck_messages_content_not_blank
        CHECK (length(btrim(content)) > 0)
);

-- The exclusivity invariant (FR-003). This is the feature, expressed as a constraint:
-- PostgreSQL will refuse a second concurrent Processing row for the same user.
CREATE UNIQUE INDEX IF NOT EXISTS ux_messages_active_per_user
    ON messages (user_id)
    WHERE state = 'Processing';

-- Serves both "next message for this user" and the sweeper's "users with pending work".
CREATE INDEX IF NOT EXISTS ix_messages_pending
    ON messages (user_id, sequence)
    WHERE state = 'Pending';

-- Serves the expiry scan.
CREATE INDEX IF NOT EXISTS ix_messages_processing_claimed_at
    ON messages (claimed_at)
    WHERE state = 'Processing';
```

The blank-value `CHECK` constraints back up FR-017 at the storage layer. Validation still happens at
the API so the client gets a useful 400, but the constraint means no code path can create an
unusable row.

Applied at startup inside `pg_advisory_lock(4919283746501)` so two instances starting together
cannot race on DDL (R-007).

## Statements

Five statements carry the whole design. They are listed here because the correctness argument lives
in their exact shape, not in the prose around them (R-006).

### 1. Accept

```sql
INSERT INTO messages (id, user_id, content, state, accepted_at)
VALUES (@id, @userId, @content, 'Pending', @now)
RETURNING sequence;
```

The moment this commits is the moment the message is "accepted", so `sequence` is the acceptance
order by construction. Nothing is acknowledged to the client before this commits (FR-022).

### 2. Claim the next message for a user

```sql
UPDATE messages
   SET state      = 'Processing',
       claimed_at = @now,
       claimed_by = @instanceId
 WHERE id = (
         SELECT id
           FROM messages
          WHERE user_id = @userId
            AND state   = 'Pending'
          ORDER BY sequence
          LIMIT 1
       )
   AND NOT EXISTS (
         SELECT 1 FROM messages
          WHERE user_id = @userId
            AND state   = 'Processing'
       )
RETURNING id, user_id, content, sequence;
```

Two guards, deliberately overlapping:

- The `NOT EXISTS` makes the ordinary case a no-op rather than an error — under no contention this
  simply returns zero rows when the user is already busy.
- `ux_messages_active_per_user` catches the case the `NOT EXISTS` cannot: two instances evaluating
  it in overlapping transactions both see no active message, and both try to write. One commits, the
  other gets a unique violation, which the caller treats as "lost the race" (not an error). This is
  the guard that makes FR-012 and SC-005 hold; the `NOT EXISTS` is an optimization on top of it.

Subselect ordering by `sequence` is what makes the claim FIFO (FR-002). The statement returns the
claimed row so the caller can submit without a second read.

### 3. Complete from a callback

```sql
UPDATE messages
   SET state          = @finalState,     -- 'Completed' | 'Failed'
       answer         = @answer,
       failure_reason = @failureReason,
       claimed_at     = NULL,
       finished_at    = @now
 WHERE id    = @id
   AND state = 'Processing'
RETURNING user_id;
```

`AND state = 'Processing'` is the whole of the idempotency story. A duplicate callback (FR-014), a
post-expiry callback (FR-013b), and a callback for an already-failed message all match zero rows and
change nothing — and because the successor claim runs only when this returns a row, the queue also
advances exactly once (SC-010). Zero rows plus an existing id means "already final"; zero rows plus
no such id means unknown (FR-015), which the API distinguishes with a separate existence check.

### 4. Expire stale claims

```sql
UPDATE messages
   SET state          = 'Failed',
       failure_reason = 'No completion callback was received before the claim expired.',
       claimed_at     = NULL,
       finished_at    = @now
 WHERE state      = 'Processing'
   AND claimed_at < @cutoff
RETURNING id, user_id;
```

`@cutoff` is `TimeProvider.GetUtcNow() - ClaimTimeout`, computed in application code so tests can
advance a `FakeTimeProvider` instead of sleeping (R-005). The same `state = 'Processing'` guard
means an expiry cannot race a completing callback: whichever commits first wins and the other
matches nothing. Returned `user_id` values feed straight into statement 2 so the queue advances in
the same sweep.

### 5. Read status

```sql
SELECT id, user_id, sequence, state, answer, failure_reason,
       accepted_at, claimed_at, finished_at
  FROM messages
 WHERE id = @id;
```

Content is not selected — the status response does not echo it, which keeps the read path free of
any reason to touch a field that must never be logged.

### Sweeper support: users with pending work and no active message

```sql
SELECT DISTINCT p.user_id
  FROM messages p
 WHERE p.state = 'Pending'
   AND NOT EXISTS (
         SELECT 1 FROM messages a
          WHERE a.user_id = p.user_id
            AND a.state   = 'Processing'
       )
 LIMIT @batchSize;
```

Feeds statement 2 for each returned user. Both instances running this concurrently is safe — the
claim decides the winner — so the sweeper needs no leader election.

## Transaction boundaries

Deliberately narrow, because Principle IV forbids holding anything across the language-model call:

| Operation | Boundary |
|-----------|----------|
| Accept | Single statement, autocommit. |
| Claim | Single statement, autocommit. **Commits before submission.** The submission to the language model happens outside any transaction; if it throws, the message stays `Processing` and expiry reclaims it. |
| Complete | Single statement, autocommit. The successor claim is a *separate* statement afterwards — deliberately not batched, so a failure to start the successor cannot roll back a completion that has already been reported. |
| Expire | Single statement per sweep, autocommit. |

No operation in this feature needs a multi-statement transaction, which is a direct consequence of
putting the claim in the row rather than in a separate lock.

## Volume

One row per submission, retained for the environment's life (FR-023). At demonstration scale — tens
of users, hundreds of messages — this is trivially small; the partial indexes stay proportional to
in-flight work rather than to history, since they cover only `Pending` and `Processing` rows.
