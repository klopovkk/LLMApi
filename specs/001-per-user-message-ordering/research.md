# Phase 0 Research: Per-User Message Ordering and Exclusivity

**Feature**: `001-per-user-message-ordering` | **Date**: 2026-08-24
**Spec**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md)

This document resolves every open technical decision before design. Each entry records the
decision, why it was chosen, and what was rejected. Nothing here is marked NEEDS CLARIFICATION:
the five spec-level ambiguities were closed in the clarification session recorded in
[spec.md](./spec.md), and the two items that session deferred to planning (performance targets
and observability) are resolved in R-008 and R-009 below.

---

## R-001: Coordination store — PostgreSQL alone, no Redis

**Decision**: PostgreSQL is the only shared store. It holds message state, per-user ordering, and
the processing claim. Redis is not used.

**Rationale**: FR-008, FR-018, and FR-023 already require durable state that survives instance
restarts and stays queryable for the environment's life, so a relational store is needed
regardless. Once the state lives in PostgreSQL, the claim can be a property *of that same row*,
which means a single statement both selects the next message and takes exclusivity — there is no
window in which two systems disagree. Adding Redis would introduce a second source of truth for
the one invariant the feature exists to guarantee (FR-003), plus a lock protocol with lease
renewal and fencing tokens, plus a split-brain mode where the lock says "free" and the row says
"processing". Constitution Principle VI requires the simplest architecture that satisfies the
requirements, and Principle III requires the claim itself to be atomic — both point at one store.

**Alternatives considered**:

- *Redis distributed lock (SET NX + TTL) with PostgreSQL for state*: rejected. The lock and the
  state can diverge under partition, and correctness would depend on TTL tuning rather than on a
  constraint. It also makes Quality Gate 6 (restart does not corrupt state) span two systems.
- *Redis alone*: rejected. Fails FR-018 and FR-023 without additional persistence configuration,
  and offers no constraint mechanism to enforce FR-003 declaratively.

**Deviation to note**: `CLAUDE.md` currently describes `docker-compose.yml` as "Postgres/Redis for
shared state". That line must be narrowed to PostgreSQL when this plan is implemented, per
Principle VII (artifact updated in the same change as the code).

## R-002: Exclusivity enforced by a partial unique index, not by application logic

**Decision**: Enforce FR-003 with a partial unique index on the message table:
`UNIQUE (user_id) WHERE state = 'Processing'`. A claim attempt is a single `UPDATE` that flips the
oldest pending message for a user to `Processing`; if a concurrent instance already won, the index
rejects the write with a unique violation, which the caller interprets as "someone else claimed
it" rather than as an error.

**Rationale**: This makes "at most one active message per user" an invariant the database cannot
violate, rather than an outcome that depends on every code path remembering to check. Principle
III demands the claim be atomic and safe under concurrency; a constraint is the strongest available
form of that guarantee, and it holds even against a code path nobody thought about — including
future ones. It also makes the violation *detectable*: if the design were wrong, tests would see a
unique violation rather than silent double-processing, which is the failure mode that concurrency
bugs normally hide behind.

**Alternatives considered**:

- *`pg_advisory_xact_lock(hash(user_id))` then read-modify-write*: rejected as the primary
  mechanism. It works, but exclusivity then lives in application discipline — a path that forgets
  the lock breaks FR-003 with no constraint to catch it, and there is no artifact in the schema
  that states the invariant. (`CLAUDE.md` offers "atomic TryClaim via Postgres advisory lock" as an
  example commit message; it is an example of message *format*, not a mandated mechanism.)
- *`SELECT ... FOR UPDATE` on the user's rows, then update*: rejected as primary. Correct, but it
  serializes on row locks held across the claim and needs care to avoid holding a transaction open
  across the language-model submission, which Principle IV forbids.
- *`SERIALIZABLE` isolation for the claim transaction*: rejected. It would work, but it converts
  races into serialization failures that every caller must retry, which is more machinery than one
  index.

**Note**: advisory locks are still used for one narrow purpose — guarding schema application at
startup (R-007).

## R-003: Ordering by a database-assigned sequence, not by timestamps

**Decision**: Each message row gets a `sequence BIGINT` from a database sequence
(`GENERATED BY DEFAULT AS IDENTITY` / `bigserial`) at insert time. Per-user FIFO order is
`ORDER BY sequence` filtered to that user. An `accepted_at` timestamp is stored for reporting only
and is never used to order.

**Rationale**: FR-002 defines order as the order the middleware *accepted* the message, and insert
into the shared store is the moment of acceptance — the same moment that makes the message durable.
A database sequence gives a single total order agreed by every instance with no clock involved.
Wall-clock timestamps cannot do this: two instances have skewed clocks, and even one instance can
produce ties at the same tick, leaving FIFO undefined exactly when concurrency is highest.

**Alternatives considered**:

- *`accepted_at` timestamp ordering*: rejected. Clock skew between instances would reorder a
  user's stream, and equal timestamps leave order undefined. This is the failure SC-002 is designed
  to catch.
- *Per-user counter incremented on insert*: rejected. Requires reading the user's current maximum
  and writing back, which is a race that needs its own locking to be correct — cost with no
  benefit over a global sequence, since only relative order within a user matters.

**Accepted consequence**: sequence values have gaps (rolled-back inserts consume numbers).
Irrelevant here: the system only ever compares sequences, never requires them contiguous.

## R-004: Dispatch — inline attempt on the hot path, background sweeper as the safety net

**Decision**: Two paths try to start work, both using the same atomic claim from R-002.

1. **Inline**: after a submission is persisted, and again after a callback moves a message to a
   final state, the handling request attempts one claim for that user before responding.
2. **Sweeper**: every instance runs a periodic background pass that (a) expires claims older than
   the configured bound and (b) attempts a claim for any user that has pending work and no active
   message.

**Rationale**: The inline attempt satisfies FR-016 ("promptly") with no polling latency on the
common path. The sweeper is not an optimization but a requirement: FR-013 expiry needs a timer
that no request will ever trigger, and the sweeper is the only thing that closes the gap where an
instance dies between persisting a submission and claiming it, or where FR-022b recovery must
resume work after the store returns. Because the claim is atomic, both instances running the
sweeper simultaneously is harmless — one wins, the other sees the unique violation and moves on.
This is also what makes the design tolerate an instance disappearing at any point: correctness
degrades to "started a little later", never to "never started" or "started twice".

**Alternatives considered**:

- *Inline only*: rejected. Cannot expire stalled claims (FR-013), and a crash between insert and
  claim leaves the user's queue stalled until unrelated traffic arrives.
- *Sweeper only*: rejected. Simpler, but every message waits up to a full poll interval, which
  makes FR-016 and the ordering tests slower and noisier than they need to be.
- *`LISTEN`/`NOTIFY` instead of polling*: rejected for now. It removes idle polling but adds a
  persistent connection per instance and a reconnect story, and still needs the sweeper for
  expiry. No requirement asks for sub-poll-interval latency.

## R-005: Expiry bound evaluated against an injected clock

**Decision**: The expiry cutoff is computed in application code as
`TimeProvider.GetUtcNow() - claimTimeout` and passed into the SQL as a parameter
(`WHERE state = 'Processing' AND claimed_at < @cutoff`). `TimeProvider` is injected, so tests
substitute `FakeTimeProvider` and advance time deliberately. `claimTimeout` is configuration, with
a production-ish default of 30 seconds and short values in tests.

**Rationale**: FR-013 is the only recovery mechanism in the system after the clarification that
callback delivery is at-most-once (FR-019a), so its test is load-bearing and must not depend on a
real 30-second wait. Computing the cutoff in SQL with `now()` would be marginally more robust
against instance clock skew but would make the behaviour untestable without sleeping, which
Principle V will not tolerate for a required scenario. Expiry is a coarse safety net whose
precision is explicitly not a correctness property (spec Assumptions), so a few seconds of skew
between instances is acceptable; a test that cannot run is not.

**Alternatives considered**:

- *`claimed_at < now() - interval '30 seconds'` in SQL*: rejected for testability, as above.
- *Real waits in tests with a very short timeout*: rejected. Timing-sensitive tests of a
  concurrency invariant are exactly the flaky tests that erode trust in the suite.
- *A test-only endpoint to force expiry*: rejected. It would prove the endpoint works, not that
  the bound is enforced, and it adds API surface that production does not need.

**Atomicity note**: expiry is itself a claim-shaped operation and uses one conditional `UPDATE`, so
two sweepers cannot both expire the same message or expire one that a callback is completing
concurrently.

## R-006: Data access with Npgsql and explicit SQL, no ORM

**Decision**: `Npgsql` directly, with hand-written SQL in one small number of named commands. No
Entity Framework Core, no Dapper.

**Rationale**: The correctness of this feature *is* the exact SQL of the claim — the single
statement, the partial index it collides with, the conditional guards. An ORM interposes a
translation layer between the design and the statement actually executed, which means reviewing
the invariant means reviewing generated SQL. Writing four or five statements by hand keeps the
invariant legible in the same file that explains it, and the query count here is far too small for
an ORM to pay for itself.

**Alternatives considered**:

- *EF Core*: rejected. Change tracking and `SaveChanges` batching obscure the statement shape that
  Principle III cares about, and its concurrency-token idiom is a weaker expression of the
  invariant than a partial unique index.
- *Dapper*: rejected as unnecessary. It would remove a little mapping code; with this few queries,
  one dependency for that is not worth it.

## R-007: Schema applied at startup under an advisory lock

**Decision**: An idempotent `schema.sql` (`CREATE TABLE IF NOT EXISTS`, `CREATE UNIQUE INDEX IF
NOT EXISTS`) is applied by the middleware at startup, wrapped in
`pg_advisory_lock(<fixed key>)` so that two instances starting simultaneously cannot race.

**Rationale**: Two instances is the normal case here, and `CREATE TABLE IF NOT EXISTS` is not
actually race-free in PostgreSQL — concurrent creation can raise a duplicate-key error on the
system catalog. One advisory lock around the whole script removes that failure mode. Keeping
schema application in the application (rather than a migration tool or an init container) means
`docker compose up` and the test suite share exactly one code path, so what tests exercise is what
runs.

**Alternatives considered**:

- *A migration tool (DbUp, EF migrations, Flyway)*: rejected for now. One table and two indexes do
  not need version tracking, and Principle VI counsels against the dependency.
- *`docker-entrypoint-initdb.d` script in the Postgres image*: rejected. It would not run for the
  Testcontainers-based tests, splitting schema definition into two places that can drift.

## R-008: Performance targets (resolves the clarification session's deferred item)

**Decision**: Targets for a local composed environment on developer hardware:

| Aspect | Target |
|--------|--------|
| Submission acknowledgement | p95 under 50 ms, p99 under 150 ms |
| Claim attempt (single statement) | under 10 ms typical |
| Status read | p95 under 50 ms |
| Latency from a message reaching a final state to its successor being claimed | under 100 ms on the inline path |
| Sweeper interval | 250 ms default (configurable) |
| Default claim timeout | 30 s (configurable; tests use milliseconds) |
| Accepted submissions | at least 200 per second sustained, two instances |
| Full required test suite | completes in under 60 s |

**Rationale**: These exist to make "no degradation" falsifiable, not because the feature has a
throughput mandate. The numbers are deliberately loose — an order of magnitude above what a single
indexed insert costs — because the property under test is ordering and exclusivity, and a tight
latency budget would produce failures that say nothing about correctness. The one number that
matters behaviourally is the successor-claim latency, since it is what a user experiences as
"messages are being answered one after another" rather than "the queue is stuck".

**Alternatives considered**: no targets at all (rejected — SC-004 and the concurrency claim in
FR-004 need something to measure against); production-grade targets (rejected — meaningless
against a Docker Compose Postgres on a laptop).

## R-009: Observability (resolves the clarification session's deferred item)

**Decision**: Structured logging via `Microsoft.Extensions.Logging` only. No metrics backend, no
tracing exporter. Every message state transition logs one event carrying `messageId`, `userId`,
`fromState`, `toState`, `sequence`, and the instance identity. Lost claim races log at Debug;
expiries log at Warning; store-unavailability logs at Error. A `GET /health` endpoint reports
whether the shared store is reachable.

**Message content is never logged at any level.** FR-021 forbids content at informational severity
*or below*, which covers Trace and Debug as well, and logging content at Warning or Error would be
a strange way to comply with a rule clearly aimed at keeping it out of logs entirely. Treating the
rule as an outright prohibition is both simpler to review and impossible to get subtly wrong.

**Rationale**: Principle II requires that it be possible to determine which message is active for
a user and whether the next may proceed — transition logs plus the queryable state satisfy that
directly. `GET /health` is included deliberately rather than as scope creep: FR-022 describes
behaviour *during* a store outage, and the outage test needs an observable signal that the
instance is up while the store is not.

**Alternatives considered**: OpenTelemetry traces and metrics (rejected — Principle VI, and no
requirement or gate asks for them); no health endpoint (rejected — leaves FR-022 states
unobservable and the outage scenario harder to assert on).

## R-010: Test strategy — real PostgreSQL via Testcontainers, two in-process instances

**Decision**: xUnit, with `Testcontainers.PostgreSql` supplying a real PostgreSQL for tests and
`Microsoft.AspNetCore.Mvc.Testing` hosting two independent `WebApplicationFactory` instances
against that one container. `FakeTimeProvider` (from `Microsoft.Extensions.TimeProvider.Testing`)
drives expiry. Cross-instance callbacks are exercised by posting the callback to the instance that
did not submit.

**Rationale**: The invariant under test is a property of PostgreSQL's concurrency behaviour, so
substituting an in-memory store would test nothing that matters — the partial unique index and the
conditional update either race correctly against a real server or the design is wrong. Two
in-process hosts sharing one container reproduce the two-instance topology (distinct application
state, shared coordination state) at unit-test speed, which is what makes it realistic to run the
whole suite after every change touching claim logic, as `CLAUDE.md` requires. Docker Compose
remains the vehicle for demonstrating Quality Gates 1–6 by hand, but is deliberately not on the
test loop's critical path.

**Alternatives considered**:

- *In-memory or SQLite store for tests*: rejected outright. It would make the tests pass while
  proving nothing about the mechanism, which is worse than no test.
- *Compose-based end-to-end tests as the primary suite*: rejected as primary. Slow, harder to
  drive time deterministically, and awkward to assert internal transitions on — though the
  quickstart keeps a manual compose walkthrough for the gates that require it.
- *Two OS processes instead of two in-process hosts*: rejected. Same coordination semantics, but
  loses direct assertion access and `FakeTimeProvider` injection.

## R-011: Fake provider delivers its callback over real HTTP to the other instance

**Decision**: The fake provider is an in-process implementation of the language-model boundary that
schedules a single HTTP POST to a configured callback base URL after a configured delay. In the
composed environment each instance is configured to call the *other* instance's callback endpoint.
Its behaviour modes are: respond after a delay, respond with a failure, or never respond.

**Rationale**: FR-006 is only genuinely exercised if the callback crosses a process boundary, and
pointing each instance at its peer guarantees the cross-instance path on every single message
rather than leaving it to a load balancer's chance distribution. The "never respond" mode is how
the FR-013 expiry and SC-004 held-message scenarios are set up without touching the code under
test, and "respond with a failure" covers FR-016's failed-state advance. Delivery is a single
attempt with no retry, per FR-019a; a failed POST is logged and dropped, which is precisely the
condition expiry exists to clean up.

**Alternatives considered**:

- *An nginx or YARP load balancer in front of the instances*: rejected. It would make callback
  routing incidental instead of guaranteed, and adds a component to the compose file that proves
  nothing the peer-pointing arrangement does not. A note in the quickstart records that a real
  deployment would place a load balancer here.
- *A separate stub service container*: rejected — the spec's non-functional constraints forbid it.
- *In-process direct invocation of the callback handler*: rejected. It would bypass HTTP entirely,
  which is the one thing FR-005 and FR-006 are about.

## R-012: Project layout follows the repository working agreement

**Decision**: Adopt the layout `CLAUDE.md` already prescribes: `src/Middleware`,
`src/LLM.Abstraction`, `src/LLM.FakeProvider`, `tests/Concurrency`. The existing `LLMApi.Api`
scaffold is relocated and renamed to `src/Middleware`, and `LLMApi.slnx` is updated to reference
all four projects.

**Rationale**: `CLAUDE.md` documents this layout as the repo's structure and its commands already
reference `src/Middleware` (`dotnet run --project src/Middleware`). Keeping `LLMApi.Api` where it
is would leave the documented commands wrong on day one. Three source projects rather than one is
not gratuitous: Principle IV requires the language-model integration to sit behind an abstraction,
and a separate `LLM.Abstraction` assembly with no provider dependency is what makes that boundary
enforced by the compiler rather than by convention.

**Alternatives considered**:

- *Keep `LLMApi.Api` and update `CLAUDE.md` instead*: viable, and cheaper by one `git mv`. Rejected
  because the working agreement was written deliberately and the constitution treats the artifacts
  as authoritative over incidental existing state.
- *A single project with folders instead of three*: rejected. The boundary in Principle IV would
  then be a naming convention, and nothing would stop the middleware referencing the fake provider
  directly.

**Target framework**: the existing project targets `net10.0` and the installed SDK is 10.0.302,
which satisfies the ".NET 9 or newer" constraint. Keep `net10.0` for every project.
